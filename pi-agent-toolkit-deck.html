Technical deep dive

Pi Agent Toolkit

How earendil-works built a coding agent out of four small, swappable pieces — and why the design choices matter for anyone building on top of LLMs.

github.com/earendil-works/pi · 8 packages · ~230,000 lines of TypeScript · MIT-licensed
Written for engineers who are new to agent frameworks. Every hard idea is broken into its own slide — use → to start.

It's not one tool. It's four, stacked.

Pi ships as a monorepo of independent npm packages. Each does one job and the next one up composes it into something bigger.

@earendil-works/pi-aiTalks to any LLM provider (OpenAI, Anthropic, Google, Bedrock…) through one interface.
@earendil-works/pi-agent-coreRuns the "ask model → run tools → repeat" loop, and remembers what happened.
@earendil-works/pi-coding-agentThe actual CLI you install and type pi to run — built from the two above.
@earendil-works/pi-tuiThe terminal UI that draws what you see on screen.
Four more supporting packages — protocol, client, server, storage, evals — get their own tour later.

A toolkit with strong opinions

  • No built-in permission prompts. Approval is something you build with a hook, not something Pi decides for you.
  • No MCP support baked in. Left out on purpose — add it yourself as an extension if you want it.
  • Sessions aren't a flat chat log. They're a branching tree, closer to git commits than a scrollback buffer.
  • Sandboxing lives outside the process. In a container or micro-VM, not in an in-app permission system.
Keep these four in mind — every later section fills in the detail behind one of them.

01
pi-ai

Talking to any LLM provider through one door.

Every provider speaks a different dialect

OpenAI, Anthropic, Google, Bedrock — each has its own request shape, its own streaming events, and its own way of describing a tool the model can call.

  • OpenAI puts the system prompt in the messages array as a role; Anthropic gives it a dedicated top-level field.
  • OpenAI streams tool-call fragments as array-indexed deltas; Anthropic sends an explicit "block start" then JSON fragments.
  • Even "max tokens" isn't one field name everywhere — some APIs call it max_tokens, others max_completion_tokens.
pi-ai's job: let the rest of Pi write code once, against one shape, no matter which of ~35 supported providers is actually answering.

Three types hold up the whole abstraction

// simplified from packages/ai/src/types.ts
type Context = {
  systemPrompt?: string;
  messages: Message[];
  tools?: Tool[];
};

type Message = UserMessage | AssistantMessage | ToolResultMessage;

type AssistantMessage = {
  content: (TextContent | ToolCall | ThinkingContent)[];
  usage: Usage;
  stopReason: "stop" | "length" | "toolUse" | "error" | "aborted";
};

Context is the normalized request. Message is the normalized shape of anything in the conversation. AssistantMessage is the normalized reply — same fields whether the answer came from GPT, Claude, or Gemini.

packages/ai/src/types.ts

One event vocabulary, regardless of provider

type AssistantMessageEvent =
  | { type: "text_delta", delta: string, partial: AssistantMessage }
  | { type: "toolcall_delta", delta: string, partial: AssistantMessage }
  | { type: "done", reason: "stop"|"length"|"toolUse", message: AssistantMessage }
  | { type: "error", reason: "aborted"|"error", error: AssistantMessage };

Every provider adapter translates its own wire format (SSE chunks, websocket frames…) into this same set of events. Each one also carries a live partial snapshot of the reply-so-far, which is what lets a UI show text streaming in.

Design lesson: a stream is contractually not allowed to throw. A failure becomes an error event carrying a synthetic message — so callers never need a try/catch around "the model might be halfway through talking."

Same tool call, two accents

The model wants to call a get_weather tool. Here's how that one idea is represented on the wire by two providers, before pi-ai normalizes it back.

OpenAI

tool_calls: [{
  id: "call_1",
  type: "function",
  function: {
    name: "get_weather",
    arguments: '{"city":"Lima"}' // a JSON string
  }
}]

Anthropic

content: [{
  type: "tool_use",
  id: "toolu_1",
  name: "get_weather",
  input: { city: "Lima" } // a real object
}]
Both converge on the exact same toolcall_delta / toolcall_end events by the time your code sees them — you never write provider-specific parsing.

Every reply carries its own receipt

Each AssistantMessage comes back with a normalized Usage: input tokens, output tokens, cache-read/cache-write tokens, and a computed cost.

1
central calculateCost()
2×
Anthropic 1h cache-write rate
~4
chars per token, rough estimate

Cost is computed from a per-model rate table ($ per million tokens), with special cases like Anthropic billing an extended cache write at double the base input rate. Before a real response exists — e.g. for a live "tokens used so far" indicator — Pi falls back to a rough four-characters-per-token estimate. Good enough for a progress bar, not for an invoice.

A flags object absorbs the chaos

Many providers are "OpenAI-compatible" but not quite. Rather than writing a new adapter for each, pi-ai gives every model a small compat flags object the shared OpenAI adapter reads.

FlagProblem it solves
maxTokensFieldSome APIs want max_tokens, others max_completion_tokens.
supportsDeveloperRoleNewer reasoning models use a developer role instead of system.
requiresToolResultNameSome providers need the tool's name repeated on the result message.
thinkingFormat~9 different ways providers encode "reasoning" tokens on the wire.
One adapter, dozens of providers — the differences become data, not code.

pi-agent-core

The loop that turns a chat model into an agent.

The mental model: what is a "turn"?

Strip away the code and an agent is a small cycle repeated until there's nothing left to do:

  1. Ask the modelSend the conversation so far.
  2. It replies — maybe with tool callsText, and/or requests to run specific tools.
  3. Run those toolsLocally, on your machine.
  4. Feed the results backAppended to the conversation.
  5. RepeatUntil the model stops asking for tools.
One reply + its tool executions = one "turn." The next slide is exactly this, but as the real code sees it.

If the model's output was cut off mid-stream ("length"), Pi refuses to run the tool calls in it — truncated JSON arguments can look valid and still be wrong.

Layer 1 of state: the stateless snapshot

type AgentContext = {
  systemPrompt: string;
  messages: AgentMessage[];
  tools?: AgentTool[];
};

The loop itself owns no memory. You hand it a snapshot — the whole conversation so far — and it hands back the new messages produced this turn. Nothing is mutated behind your back.

This is a deliberate design choice: keep the engine a pure function, and put statefulness in a thin wrapper around it (next slide).

Layer 2: the live object you actually hold

The Agent class wraps the pure loop and tracks what's happening right now:

  • isStreaming, streamingMessage — is a reply currently arriving, and what does it look like so far?
  • pendingToolCalls — which tool calls are still running.
  • agent.steer(msg) — inject a message while the model is mid-turn.
  • agent.followUp(msg) — queue the next prompt for after this turn finishes.
  • agent.subscribe(listener) — get every event as it happens.

Layer 3: history as a tree, not a list

%%{init: {'theme':'base','themeVariables':{'primaryColor':'#20232c','primaryTextColor':'#dfe2ea','primaryBorderColor':'#f0b429','lineColor':'#6fd3c7','tertiaryColor':'#1a1c23','fontFamily':'ui-monospace, monospace','fontSize':'14px'}}}%%
flowchart LR
  R((start)) --> M1[user msg] --> M2[assistant + tool call] --> M3[tool result]
  M3 --> M4[assistant reply]
  M4 --> B1["branch A\n(kept)"]
  M4 --> B2["branch B\n(abandoned, summarized)"]
  B1 --> L(("leaf pointer\n= 'here'"))

Every entry (a message, a model change, a compaction event) has a parentId. A "leaf" pointer marks where you currently are. navigateTree() can move that pointer to any earlier point — like git checkout — and can even generate an LLM summary of the branch you're leaving behind.

This one structure is what later powers /fork, /tree, and /resume in the CLI.

What actually happens when a tool gets called

%%{init: {'theme':'base','themeVariables':{'primaryColor':'#20232c','primaryTextColor':'#dfe2ea','primaryBorderColor':'#f0b429','lineColor':'#6fd3c7','tertiaryColor':'#1a1c23','fontFamily':'ui-monospace, monospace','fontSize':'14px'}}}%%
flowchart LR
  A[model asks for a tool] --> B[look it up by name]
  B --> C[prepareArguments]
  C --> D[validate against schema]
  D --> E{beforeToolCall hook}
  E -- blocked --> F[error result,\nnever executes]
  E -- allowed --> G["execute(signal, onUpdate)"]
  G --> H[afterToolCall hook]
  H --> I[turned into a ToolResultMessage]
  I --> J[fed back into the conversation]
Every safety decision funnels through one seam: the beforeToolCall hook. It's the only place that can say no.

Tools can run at once — carefully

By default, if the model requests several tool calls in one reply, Pi runs them in parallel. Two exceptions force sequential execution: the caller sets a global "sequential" mode, or an individual tool declares itself executionMode: "sequential" (a tool that isn't safe to run concurrently with itself, for instance).

Even in parallel mode, permission checks (beforeToolCall) still run one at a time, in order — only the actual execute() calls happen concurrently. Results are reassembled back into the model's original order regardless of which one finishes first.

There's no approval system — there's a hook

At this layer, "permission" isn't a feature. It's one optional function:

beforeToolCall(call) => { block: true, reason: "needs human approval" }
// returning this prevents execution and injects an error result instead

That's the entire mechanism pi-agent-core provides. It doesn't decide what "asking permission" looks like, or when to ask — that's left to whoever builds on top. Keep this in mind for the next section, because the CLI built on top of it makes a very deliberate choice here.

What happens when the conversation gets too big

Every model has a context window — a maximum number of tokens it can see at once. Pi checks usage against that limit every turn and, when it gets close, compacts:

16,384
tokens reserved as headroom
20,000
most-recent tokens kept verbatim

Older messages are summarized by a dedicated LLM call, the summary replaces them, and the recent tail is kept exactly as-is. The whole operation is recorded as its own entry in the session tree from two slides ago — compaction doesn't erase history, it adds a node that says "everything before this point became a summary."

Four patterns worth stealing

  • Pub/sub over the loop. subscribe()/on() let any number of listeners (a UI, a logger, a test) observe the same run without coupling to it.
  • Hooks as middleware. beforeToolCall, afterToolCall, transformContext, prepareNextTurn are injection points around an otherwise closed loop.
  • Pure core, stateful shell. The loop is a function; Agent and the harness are the classes that hold state around it.
  • Result<T, E> over exceptions. Expected failure paths (compaction, summarization) return a typed result instead of throwing.

pi-coding-agent

The CLI you actually type pi to run.

Seven tools, on by default

ToolWhat it doesNotable detail

Notice what's missing from the "notable detail" column on bash: nothing. That's not an oversight — it's the topic of the next slide.

"It intentionally does not include permission popups"

That's a direct line from Pi's own docs. By default, the CLI runs with the full permissions of the process that launched it — no per-action confirmation dialog exists.

What does exist is narrower than it sounds:

  • Project trust — a one-time yes/no on whether to load project-local config, extensions, and skills at all. Not a per-action gate.
  • beforeToolCall hook (from pi-agent-core) — the seam a third-party extension can use to build its own confirmation prompt, e.g. before rm -rf.
  • Static tool filters — flags like --tools / --exclude-tools disable whole tools at startup. A config-time allowlist, not a runtime prompt.

If you want a fence, build it around the process

Since there's no in-app sandbox, isolation is pushed to the OS or VM boundary, in three documented patterns:

PatternIsolation boundaryWhat stays on the host
Gondolin extensionBuilt-in tools & shell commands run inside a local Linux micro-VM.Pi itself, and your provider credentials.
Plain DockerThe entire Pi process runs inside one container.Nothing — API keys are passed into the container.
OpenShellThe entire process runs inside a policy-controlled sandbox (filesystem/network/credential rules).Real API keys — the sandbox talks to a local proxy that injects them upstream.

Every conversation is a save file

Sessions persist to disk as an append-only log, using the same tree structure covered earlier — so a session isn't just resumable, it's branchable.

pi -c              # continue the most recent session
pi -r              # pick a past session interactively
pi --fork <id>     # branch a new session off an old one
/tree              # navigate the session's branch structure
/compact           # manually trigger the summarize-and-cut from earlier

Small core, everything else is a plugin

  • Extensions — TypeScript modules that can register custom tools, register slash-commands, and hook into any lifecycle event.
  • Skills — self-contained folders of instructions and scripts, loaded on demand, following the community "Agent Skills" convention.
  • Pi packages — installable bundles of extensions, skills, and prompt templates (pi install npm:@foo/bar).
  • No MCP, on purpose. The maintainers' stated position: keep the core small, and let you add an MCP client as an extension if you need one — rather than owning that complexity by default.

From pi ... to a running agent

  1. Parse argumentsTurn argv into a typed options object.
  2. Resolve the modeinteractive, print (-p / piped input), json, or rpc.
  3. Resolve the sessionNew, continued, resumed, or forked.
  4. Resolve project trustShould local config/extensions even load?
  5. Build runtime servicesSettings, model list, extension/skill loader.
  6. DispatchHand off to the right mode's runner.

The supporting cast

tui, protocol, client, server, storage, evals.

pi-tui: redraw only what changed

"Differential rendering" here means a row-level diff, not a full repaint: every frame renders the whole screen into an array of strings (one per terminal row), then compares it line-by-line against last frame's array.

Frame N
$ pi
Thinking...
> reading file.ts
→
Frame N+1 (only changed rows repainted)
$ pi
Done. 3 files edited.
> running tests...

The cursor jumps straight to the first changed row and rewrites only through the last changed row — similar in spirit to React's virtual-DOM diffing, applied to terminal lines instead of DOM nodes.

Messages are CBOR-encoded, length-prefixed, and sent over a Unix domain socket; the server checks a SHA-256 token before accepting a connection. This is deliberately transport-neutral and still marked experimental — the shipped CLI's own terminal mode doesn't use it, and talks to the agent in the same process instead.

Same DAG from the pi-agent-core section — SQLite (with WAL mode) is just where it lives on disk.

pi-evals: testing an agent means testing it live

You can't unit-test "does the model behave correctly" the normal way. pi-evals is a vitest-based framework that spins up a real agent session and runs it against a live model.

  • Some checks are simple — "does it answer this correctly, and report non-zero token usage."
  • Others use an LLM as a judge, scoring free-form answers for quality.
  • Every run's transcript and scores are saved as artifacts, so a prompt or model change can be tracked for regressions over time.

What to steal for your own agent

  • Separate a pure loop from its stateful wrapper. Testable engine, thin state on top.
  • Model history as a tree the moment you need branching or undo — retrofitting it onto a flat array later is painful.
  • Make permissions a hook, not a hardcoded prompt. Let the app built on top decide what "asking" means.
  • Normalize provider differences into one event vocabulary early. Do the messy translation once, at the edge.
  • Keep the core small; push policy to the edges. Sandboxing, MCP, and permissions are all "bring your own" in Pi — and that's the point, not a gap.
